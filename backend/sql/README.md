# Schema privado do FILTROX

`001_init.sql` define as tabelas privadas de histórico, favoritos e equivalências. Cada linha pessoal é identificada pela chave `actor_id` e pelo `video_id`; a chave primária composta permite manter o mesmo vídeo uma vez por conta. A API obtém `actor_id` do `Principal` criado somente após autenticar o único e-mail configurado no servidor. O identificador é um SHA-256 do e-mail normalizado, não é recebido do navegador e não substitui a autenticação.

As rotas e queries de leitura, inclusão e remoção sempre filtram por `actor_id`. O frontend recebe apenas os campos do item pessoal e a data; não recebe o identificador da conta. Isso permite que aparelhos autenticados com a mesma conta compartilhem o estado quando apontam para a mesma instância PostgreSQL. Os endpoints autenticados `/v1/me/history/export` e `/v1/me/favorites/export` aceitam `format=csv` ou `format=json`, consultam todas as linhas do admin e projetam somente ID, URL, fonte e data; nenhum actor informado pelo cliente, credencial, hash, token ou catálogo é exportado. Não há tabela de cadastro público. A migração `002_admin_credentials.sql` cria um único registro permitido para `owner`, contendo somente o hash PBKDF2 da senha e a data de alteração; a primeira troca inicializa esse registro a partir do hash bootstrap do servidor. Senhas em texto puro nunca são persistidas.

O backend não aplica migrações ao iniciar. Para uma base PostgreSQL nova e vazia, a execução é explícita: exporte `DATABASE_URL` no ambiente do processo e rode `PYTHONPATH=backend python3 backend/scripts/migrate.py`. O executor registra versões em `filtrox_schema_migrations`, usa transação por arquivo e lock advisory do PostgreSQL. Ele se recusa a aplicar migrações se encontrar tabelas de aplicação sem histórico de versões; um baseline de base preexistente exige revisão separada. A troca de senha e os downloads de dados pessoais só funcionam depois de provisionar PostgreSQL e aplicar as migrações; o banco ainda não foi provisionado.

Os testes do repositório usam conexões/pools simulados e valores sintéticos. Nenhum teste provisiona, conecta ou migra um banco real. Trocar a senha não encerra sessões já abertas; elas continuam sob a regra existente de encerramento local ou expiração após 30 dias sem atividade, sem logout remoto global. Antes de usar PostgreSQL de verdade, ainda é preciso preparar a infraestrutura privada aprovada, configurar `DATABASE_URL` como segredo server-side com TLS `verify-full` e aplicar migrações em procedimento revisado.

## Backup manual local

A tela autenticada `/settings` permite iniciar cada exportação manualmente. `GET /v1/admin/backups` apenas verifica configuração local; `GET /v1/admin/backups/download` inicia `pg_dump` e transmite seus bytes diretamente por um pipe para `age`, e somente o texto cifrado chega ao download do navegador. Não há diretório de backup no servidor, staging de dump, retenção, criação automática, cron ou scheduler. O navegador baixa o arquivo `.dump.age`, que o proprietário deve salvar no aparelho/local escolhido.

Configure `FILTROX_BACKUP_AGE_RECIPIENT` apenas no backend privado aprovado com a chave pública `age` correspondente à identidade privada guardada sob controle do proprietário. O backend nunca precisa da identidade privada. O `DATABASE_URL` deve ter `sslmode=verify-full`; com senha, o Linux precisa oferecer `memfd_create` e `/proc/self/fd`, para que a credencial seja entregue por passfile anônimo em memória, nunca por `PGPASSWORD` ou arquivo temporário. `age` e `pg_dump` são aceitos somente em `/usr/bin:/bin` quando root-owned e não graváveis por grupo/outros. Nenhuma hospedagem foi escolhida, então a exportação real permanece indisponível até a infraestrutura ser aprovada e configurada.

A restauração está bloqueada: ainda não existe um caminho validado para enviar um arquivo local, descriptografá-lo com a chave privada local e entregar/salvar localmente um backup pré-restauração antes de qualquer alteração. Não há flag que habilite esse caminho. Nenhum banco real, `pg_dump`, `age` ou restauração foi executado nesta revisão; a cobertura será por processos simulados e dados sintéticos.
